# Research and incremental updates

For discovery, prefer existing local leads and primary repositories/docs; search GitCode, Gitee and GitHub with framework aliases plus HarmonyOS/OpenHarmony/OHOS/鸿蒙/PC/2in1. Screen at most 20 new candidates across up to three query families unless the user requests a larger scope. Save a no-new-project result when exhausted; don't silently reanalyze old sources or schedule monitoring.

Qualify an adaptation from actual source/build inputs: native host, selected target/backend, runtime artifacts, platform branches and bridge implementations. README claims and desktop UI alone are not proof. Electron support needs the actual runtime/Chromium/Node and host integration; RN needs the resolved OH native adapter and modules; KMP needs the actual Kotlin target/toolchain and interop boundary. Do not equate a similar renderer, JVM embedding or generic C ABI with a working framework port.

Record canonical URL, aliases/fork family, framework, selected ref, observed commit, analyzed commit, license and managed checkout location in `maintenance/sources.json` (schema_version 1, sources array). Reuse identity after verifying mirrors; identical commits and patch-equivalent forks are duplicate evidence. Keep clones outside `knowledge/` and preserve their worktree, index and branch.

For explicit updates, fetch recorded refs without checkout/reset/clean. Compare the previous analyzed commit to observed commit. Inspect merge-aware diffs, relevant shared-code changes, follow-up fixes and reverts, not just OH commit subjects. Read from pinned objects, or hash working files when the user specifically requests uncommitted work. Unchanged sources need no reanalysis. Missing refs, ancestry or access stay incomplete; don't replace a branch without a justified user decision.

Each run in `maintenance/runs/*.json` records mode, source IDs, ranges/snapshot hashes, outcome, added/extended/split entries, limitations and verification performed. For history updates, include a disposition for every screened commit: reviewed, duplicate, irrelevant or deferred with reason. Advance analyzed_commit only after all required review is complete and index/check pass. Retain old analyzed_commit on partial/deferred review; observed_commit may advance independently.

For imported databases, retain their project registry as a source snapshot, not as proof those projects were independently reviewed in this database. Import coverage maps source document paths to all resulting entry IDs, including split/merge dispositions. Record omitted orchestration/template/index material and why. Pin license notices and preserve source-reported verification separately from current execution.

For knowledge-collection updates, compare the current source file inventory and per-file hashes with the imported snapshots/map, including untracked and modified files. An unchanged HEAD does not mean unchanged working content. Reimport only changed/new documents, reconcile removed documents without blindly deleting curated knowledge, and preserve many-to-many split/merge mappings. Collection imports can retain analyzed_commit:null because their underlying projects were not independently reviewed; record completed collection snapshot review separately. When both inventory and hashes are unchanged, report no changes without reanalysis.
